# 档案小谷自动整理流程

上传中心和原档案上传共用 OCR、原件存储和职工资料，不另建影子档案。

- 运行 `database/migrations/V026__a_archive_automation.sql` 后部署新 WAR；该迁移只新增流程表，不回写现有职工资料，也不会批量审批旧报告。
- 每份新上传报告创建一项可追踪的档案小谷任务，幂等上传不会重复建任务。后台持续运行，关闭浏览器不影响处理。已有报告可点击上传中心“上传处理详情”恢复并启用自动整理。
- OCR 完成后读取当前单位数据库的职工姓名、工号、完整手机号、性别、出生日期，以及原系统已合法关联的身份证号。仅通过已有单位授权关系查证身份证号，接口不返回完整证件号码。
- 当前策略（identity-v3-name-sex-contact）：姓名、性别一致，且完整身份证号或完整手机号一致并唯一匹配到一名职工，才自动关联。三个字段均须有报告原件证据；工号单独一致不再触发自动关联，缺少性别或身份冲突、匹配多人转人工。工号、岗位和出生日期不作为自动处理前提，不覆盖职工基础资料；医疗审核状态独立保留。
- 工号、部门 / 班组、岗位 / 工种在 OCR 工作台显示为只读基础资料；不要求报告包含，不将基础资料伪装成 OCR 原文，也不从报告自动覆盖花名册。
- 已关联后自动检查同人、同日期、同机构的疑似重复报告，保留原件与历史报告关系；报告分类不确定、日期无法确定或资料缺项时展示待补清单，不覆盖已有结果。
- 资料满足原系统送审规则时，档案小谷准备有效报告日期并自动提交医生最终审核。系统不会调用批准或归档操作。医生审核并归档后，沿用现有 AI 体检评估队列创建评估小谷任务，并遵守评估服务配置及队列上限；未配置或暂停时保留任务与错误，稍后重试。
- 原件指纹去重继续由已有上传服务负责；疑似重复不自动合并。身份证或工号未能从原件确认时允许健康管理员人工核验，已绑定报告改绑仍要求医生权限。

流程表保留 `match_score`、`match_status`、`match_reason`、`matched_fields`、`conflict_fields`、`decision_mode`、`confirmed_by`、`confirmed_at`、检查结果与评估批次。自动操作同时写入数字员工执行事件和档案操作日志。流程任务由后台负责，不通过普通派活的生成按钮重复执行。

接口：`GET/POST /ehr/api/report-center/{reportId}/{revision}/automation`。POST 为登录后台的显式恢复操作，沿用 CSRF 和单位权限。报告详情也返回 `automation` 状态。

回归：`ArchiveAutomationChecks` 使用隔离的 `shayu_3_preview`、真实 MySQL 与 OCR 接收契约验证自动送审、身份冲突、日志及幂等；所有数据回滚，不请求外部模型。评估衔接使用假实现验证调用，现有 `AiExamChecks` 单独覆盖真实队列表结构和权限。浏览器夹具覆盖基础资料只读、数据来源标识、自动处理状态和免重复人工确认；不向实际档案写测试报告。


### 2026-11-26：多格式原件核验修复

`archive-quality-v7-context` 保留表格数值之间的空白边界，避免把结果与下一列的单位、参考范围拼接；仍拒绝数值子串、正负号及指数不一致。同名观察按来源页、单位、参考范围分别比较；“既往史、其它”等通用分科标签具有独立原文证据时分别保留，不合并为一个结果。

矫正视力在原件同名行明确空白时记入 `notReportedItemIds`，不当作正常值，不发送给健康评估；缺失的检验值及无原件支持的空白仍需核验。总检结论的原文完整匹配且存在总检签署边界时，可通过行政资料完整性核验，保持原医疗审核状态。

已有异常记录由新版规则重新计算并自然解除，旧原件、OCR证据及行政入档版本保留。评估任务先完成接单日志和入参校验，再写入运行状态，避免接单未完成却显示执行中的悬挂状态。

原报告没有医师建议时，`a_health_advice` 保持空，不作为完整度缺项或归档异常；评估小谷产生的健康建议保存于独立 AI 评估结果，不伪装为医院原文。共享数据库的新版匿名评估任务由 V032 接单代际校验保护，旧工作进程不能无版本标记地抢占执行。
