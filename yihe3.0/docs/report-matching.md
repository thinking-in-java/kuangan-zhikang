# 报告匹配与核对

独立入口：`/assets/report-center/matching.html`，对应管理平台“报告与档案中心 → 报告匹配与核对”。页面按参考图实现左侧五项统计、筛选、报告列表及批量操作，以及右侧原件摘要、匹配结果、职工选择和校对记录。保留既有外部导航，工作区不显示遮挡按钮的健康师浮窗。

## 数据与规则

- 当前单位、当前数据模式、有效职工关联报告的当前版本进入列表，不读取其他单位或已删除职工数据。
- 原始姓名、工号、手机号、单位和班组用于规则匹配。身份证只脱敏展示；现有花名册没有可用的身份证原文，不宣称完成身份证精确比对。
- 规则版本 `report-identity-rules-v1`：姓名一致30分、工号一致60分、手机号一致60分、单位一致5分、班组一致5分，上限100分。分数仅为字段一致性规则得分，不是概率或识别置信度。
- 唯一候选满足姓名一致且工号/手机号强标识一致、没有其他身份冲突时才建议“精确匹配”。同名、单字段命中或多值冲突需人工核验；同名本身不算精确匹配。
- 已确认匹配在身份字段或所选职工版本变化后失效，重新进入待核验状态。审核/归档版本锁定，不允许从匹配页面覆盖关联。
- 顶部统计随日期、来源、搜索条件变化；状态筛选不改变这些统计口径。“已确认 / 归档”为两种状态汇总，待匹配包含未人工确认的建议结果。

## 人工操作

“保存校对结果”仅保存候选选择。只有“确认匹配并关联”在显式身份确认后才可变更关联。改绑另一职工还需医生权限、明确改绑确认；信息缺失或冲突时必须额外人工核验及至少10字说明。

识别任务进行中不能确认匹配。存在历史审核/归档版本的报告不可改绑；原职工仍有进行中数字员工任务时也拒绝改绑，以防任务上下文与报告归属错位。

实际改绑只修改未审核当前报告的 `record_id`，保留原始报告身份字段和两位职工的花名册，刷新双方资料完整度，保存经办人、原因和旧/新关联记录。不会自动审核、归档、生成干预或发送通知。

“无匹配”和“待复核”标记不删除报告，也不擅自解除已有档案关系。批量匹配首先只分析；批量确认仅允许唯一强标识建议且与当前关联一致的报告，跨职工改绑必须逐份核验。批量操作逐份事务，部分失败时明确提示已完成份数；不承诺跨报告整批回滚。

## 部署与接口

应用启动前对目标数据库执行 `database/migrations/V016__a_report_matching.sql`。它只创建匹配状态表，不为已有报告伪造人工确认记录。操作历史复用现有档案审计表。

- `GET /ehr/api/report-center/matching`：分页、匹配状态、体检日期、来源、姓名/工号/身份证/文件名搜索。
- `GET /ehr/api/report-center/matching/employees?search=...`：当前单位有效职工搜索，返回职工选择必需字段和版本，不返回手机号原文。
- `GET /ehr/api/report-center/matching/{id}/{revision}`：当前报告匹配详情、候选依据、原件和真实校对记录。
- `POST /ehr/api/report-center/matching/{id}/{revision}`：需要 CSRF、`If-Match`、UUID 请求幂等键及处理说明。`action` 为 `selection`、`confirm`、`unmatched`、`flag`。

列表导出遵守当前筛选，最多5000份，身份证保持脱敏并防止 CSV 公式注入。原件预览采用本地 PDF.js，不向外部预览服务发送文件。

## 验证

`tests/ehr/java/ReportMatchingChecks.java` 只允许隔离的 `shayu_3_preview` 数据库。29项检查涵盖候选规则、重名消歧、脱敏、保存与确认的区别、幂等性、版本冲突、OCR处理中限制、改绑权限、身份冲突、原始资料不变、关联日志、失效规则、单位隔离、参数校验及审核后锁定；全部测试写入回滚，不调用模型。

浏览器验证覆盖三种宽度、真实 PDF 预览/翻页、标签切换、手工选择、409冲突处理、批量分析、显式确认、筛选分页刷新、脱敏导出和系统菜单。浏览器写请求在测试中拦截返回409，未向现有业务库保存演示匹配或执行真实改绑。
