# 数字员工派活与独立模型服务

档案补全任务已增加**原件逐项核对**，部署需要 V013。此类任务会读取原始报告与录入项目，不再仅基于下述摘要生成自由文本。原件处理、结果分类、隐私范围与验证结果以 [digital-worker-original-check.md](digital-worker-original-check.md) 为准；下述只发送完整性摘要的说明适用于其他通用任务。

本模块从数字员工专用配置文件读取 baseUrl、apiKey、model、apiStyle、reasoningEffort、serviceTier 和读取超时。原 OCR 参数仅用于初始化复制，之后分别维护。支持 responses 和 chat_completions。密钥只由后端读取。

## 启用

先按顺序应用 V010、V011、V012 数据库迁移。V012 为每次 AI 请求保存档案完整性摘要及读取时间。作者的 V008、V009 用于数字健康师和小程序智能体，保留原编号；本模块的两个建表脚本已顺延。已通过旧编号应用本模块建表脚本的环境无需重建表，脚本内容未改变。必须通过 `--ehr.digital-worker.model-config-file=<数字员工专用私有配置文件绝对路径>` 或 `EHR_DIGITAL_WORKER_CONFIG_FILE` 指定独立文件，不会回退读取 `ehr.recognition.config-file`。此参数不会开启原有 OCR 报告队列。配置文件应放在版本控制和 Web 静态目录之外并限制文件访问权限。

打开数字员工工作台的“给 TA 派活”，核对任务类型、标题、会员编码与补充要求。处理服务已配置时，可勾选 AI 处理。现有任务可在详情中选择“读取业务资料并生成结果”。页面不展示 API 名称、模型型号或凭据。

涉及具体职工时，使用姓名或工号查找，明确选择当前单位的授权档案；也可以直接填写唯一工号。任务标题中的姓名不会自动关联，避免同名误配。已有任务可在详情中关联档案；更换档案时，待审核任务回到待处理，并把旧草稿标为未使用当前关联档案，需重新生成后审核。

## 状态与边界

- 创建任务与请求模型是两个独立步骤；请求失败不会丢失已保存的任务。
- 请求进入持久化队列，任务变为处理中；模型生成成功后，保存草稿与用量并转为待审核。
- 连接中断、超时、429、502、503、504 最多请求两次；其他错误直接记录安全错误代码。失败任务回到待处理，可手动重试。
- 同一任务只允许一个活动请求。任务版本变化或取消后，迟到结果不再应用。进程中断后的过期请求会记录失败，供人工重试。
- 模型输入包含员工岗位、任务类型、标题、补充要求，以及明确关联档案的完整性摘要：系统状态、系统完整度、按现有9项规则实时核对的完整度与缺项、最新报告版本及审核归档状态、日期机构、原件数量和页数、检查项目及结论数量。模型不收到档案姓名工号、联系方式、报告原件或临床项目原值；用户写入标题和补充要求中的内容仍会发送给模型。
- 摘要沿用健康档案页面的单位权限和缺项规则，不会修改档案或完整度缓存。资料完整度100%不代表临床风险评估完成。模型生成前重新检查请求医生的账号状态、单位、权限和档案可用性。
- 每次请求保存当时采用的摘要。详情展示“当前关联档案”与“本次草稿使用的档案数据”，草稿是读取时的快照；重新生成会读取最新档案。历史无档案摘要的结果保留，不伪装为已经读取过档案。
- 草稿按普通文本展示。模型不会修改档案、发送通知或自动执行健康干预。审核通过只完成派活任务；实际业务操作继续使用原业务模块的权限与审核流程。
- 查询与处理沿用现有登录、机构范围及数据模式；变更要求医生权限、CSRF 和任务版本校验。

## 验证

Maven 在项目根目录执行 `mvn -pl yihe-admin -am verify`。接口与浏览器试跑应在隔离数据库中使用合成任务；不得为了连通性测试将真实健康档案发送给模型。页面每三秒查询活动 AI 请求状态；任务列表继续沿用现有自动刷新。

`tests/ehr/java/DigitalWorkerArchiveChecks.java` 使用隔离预览数据库和事务回滚，覆盖实际完整度读取、跨单位拒绝、字段最小化、关联旧任务、过期版本、重复请求、已删除档案、账号权限变化及审核状态；不会调用外部模型。编译时一并编译 `HealthAgentChecks.java`，复用其合成报告夹具。
